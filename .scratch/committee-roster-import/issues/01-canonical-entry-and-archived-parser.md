# 01: Canonical roster entry, format registry, and the archived workbook parser

**What to build:** A roster parser turns one file of one known format into a canonical list of
roster entries, so that nothing downstream ever needs to know what a column is called. This
ticket builds the shape, the registry that formats register into, and the first parser: the
`Committee` / `Serve LT` / `Serve ED` workbook that the importer reads today. No caller
changes yet — the parser is proven against a real sample of the file it reads, which is the
thing no test in the repo does now.

The canonical entry carries `vrcnum`, `committee` (`cityTown`, `legDistrict`,
`electionDistrict`, already normalized), `claimed` (`name`, `address1`, `city`, `state`,
`zip` — what the county asserts about the person), `membershipType`, and `sourceRow` (1-based,
for reporting rejections). `membershipType` is required, not optional. A parse returns
`{ entries, rejected: [{ sourceRow, reason }] }`: parsers never throw on a bad row, only when
the file as a whole is not the declared format.

The registry is a flat map from format identifier to `{ label, status, parse }`, with `status`
either `current` or `archived`. This parser registers as `committee-export-xlsx` with status
`archived` — it reads a Committee Term that is already loaded and must never be fired at a new
one, but it is kept and tested so a local database can still be seeded from it, and because a
second parser is what proves the canonical shape is format-neutral rather than a rename of one
format's columns.

Format quirks are resolved inside the parser: `cityTown` uppercased, a `Committee` value
containing `LD ` meaning Rochester, trailing whitespace trimmed. `membershipType` derives from
`election type` — a value beginning `Primary Election` is `PETITIONED`, one beginning
`Executive Committee Appointed` is `APPOINTED`, anything else rejects the row.

The 2024 `DemocraticCommitteeExport` format is deliberately not implemented; it describes the
same term as this one, less completely, so it has no consumer.

## Comments

Landed as `apps/frontend/src/app/api/admin/bulkLoadCommittees/rosterFormats/` —
`types.ts` (canonical entry, parse result, format shape), `committeeExportXlsx.ts`
(the archived parser) and `index.ts` (the registry, plus `parseWithFormat`,
`isRosterFormatId` and `CURRENT_ROSTER_FORMAT_IDS`). No caller changed.

Decisions worth knowing:

- `sourceRow` is the 1-based row number in the source file **counting the header row as
  row 1**, so the first data row is row 2. The same convention holds for the delimited
  Board of Elections file, which keeps rejection reports comparable across formats.
- Format detection on read is a header-column check, not a sniff: the parser throws
  unless the workbook declares all ten columns the two workbooks share. That is enough
  to reject the 2024 `DemocraticCommitteeExport` layout and the Board of Elections CSV,
  both of which are covered by tests.
- Zero-padded districts are parsed with an explicit base-10 `parseInt` behind a
  `/^\d+$/` guard, and a district of `0` is treated as missing — matching the
  importer's current `!legDistrict` rejection.
- Fixtures live in `apps/frontend/src/__tests__/fixtures/rosterFormats/` and are
  regenerated by `pnpm --filter voter-file-tool run fixtures:roster`
  (`scripts/makeRosterFixtures.ts`), which builds each file from data held in the
  script itself: the delivered header row, column order, cell types and layout quirks,
  with 20 rows of invented people — no real name, address, phone, email, date of birth
  or VRCNUM. The script also emits the Board of Elections fixture used by
  [[05-boe-elected-list-parser]].
- The 2026-04-16 excerpt is deliberately spread across committees so it carries both the
  Rochester `LD ` case and a mixed-case town, and both `election type` values.
